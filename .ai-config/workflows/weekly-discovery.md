# 週次の課題発見と採用

候補発見・Discussionでの独立投票・採用Issueの引渡しを扱う。
対象repoのAGENTS.md・規約・公開範囲・操作許可を確認し、外部スケジュールや自動投稿は有効化しない。
repo側の最上位セッションが[役割と受け渡し](agent-handoff.md)に従って専門agentを直接呼ぶ。
採用候補は必ずIssueへ永続記録し、Coordinatorが日次でIssue担当へ依頼する。週次担当から実装を直接起動せず、必要性を再投票しない。

## 1. 対象と2系統を固定する

対象 repository、週の開始/終了と timezone、確認する固定 head、既存 Discussion/Issue/PR、実行URLを記録する。
repo と週範囲が同じ先行実行・記録を再取得し、再開なら既存候補と結果を引き継ぐ。
日次 Issue 対応と別の常駐サーバーや新しい実行基盤を作らない。

同じ repo/週でも、バグ発見とリファクタリング発見を別の独立した調査担当・会話の2系統で起動する。
互いの候補や判断を入力に混ぜない。
バグは既存仕様からの逸脱・再現条件・影響、リファクタは動作維持で解消する構造問題・狙い・回帰リスクを示す。
曖昧な仕様をバグと断定しない。

根拠は既存コード・仕様・失敗記録・Issue/PR・レビューの必要最小限に絞る。
対象 repo へ共有可能な安全な根拠だけを使い、秘密/ignored や生の私的ログを読まない。
private repo の情報を公開 Discussion・共通ルールへ転載しない。公開範囲が判断できなければ投稿を止める。

## 2. 候補を整理し Discussion に残す

Discussion は `repository / 週範囲 / 系統` ごとに1つとし、bug 用と refactor 用を別 Discussion にする。
候補ごとに Discussion を増やさず、repository・週範囲・系統はタイトルなど既存の識別情報に置き、候補の見出しに候補ID/版、内容に出典を付ける。
内容・根拠には問題・影響・最小案・期待する改善・未確定点を必要な範囲で短くまとめる。バグとリファクタを同じ候補に混ぜない。
同じ原因・同じ狙いの実質同候補、既存 Issue、過去候補の重複を比較し、別名や別系統で新規起票しない。
既存 Issue があれば根拠を追記/参照し、新規候補との対応と新規作成しない理由を残す。

許可された投稿担当が対象 repo の既存 Discussion を全ページ確認し、同じキーの候補・投票記録を再利用する。
新規投稿前に現物を再取得する。再実行・再開・応答不明でも Discussion/Issue を重複作成しない。
投稿結果が unknown なら記録と現物の照合が済むまで再送しない。未保存の本文と blocker を保持する。

### Discussionテンプレート

bug・refactor・改善で次の形式を共通に使い、候補ごとに見出しを作る。
調査が完了し候補がない場合、本文は「候補なし」のみとする。未完了や調査失敗を候補なしにせず、理由と再開先を残す。
repository・週範囲/timezone・系統はタイトルなどで識別し、固定head・実行URL・保存状態は再開記録から辿れるようにする。

```markdown
## <候補ID / 版: 短い題名>
- 内容・根拠: <問題・影響・最小案と出典、必要な未確定点>
- 投票: <賛成N / 反対N、主な理由。独立5人全員がこの候補/版を完了、または未完了の理由>
  - <担当ID 1>: <賛成/反対>・<理由>
  - <担当ID 2>: <賛成/反対>・<理由>
  - <担当ID 3>: <賛成/反対>・<理由>
  - <担当ID 4>: <賛成/反対>・<理由>
  - <担当ID 5>: <賛成/反対>・<理由>
- 判断: <採用/見送り/未完了と理由。採用Issue URL・保存確認、未保存ならその状態>
- 備考（必要な場合のみ）: <残る注意点、再確認条件など>
```

各票の対象版・完了状態は共通記載し、例外がある票だけ対象/状態を個別に書く。
全5票の完了・対象一致を確認できない間は「未完了」とし、未着票を埋めたり有効な集計として扱ったりしない。
主な理由にまとめても各担当の賛否と理由を各1行で保持し、原票の意味を変えない。旧版の票も版付きで残す。
効果測定の事前指標・before/afterは[改善Issue](development-improvement.md#3-実施前に効果の測り方を決める)側へ置き、Discussionへ重複記載しない。

## 3. 独立5人の投票

候補ごとに同じ候補ID・版・根拠・評価対象を5人の新しい独立担当へ渡す。
先行票・他担当の会話・実装側の自己正当化を継承させず、1人1票で `賛成/反対` と理由を返してもらう。
担当ID・対象・完了状況・票・理由を Discussion の記録へ対応させる。投票担当は読取専用で投稿・起票しない。

独立5人中3人以上の賛成を採用基準とする。5人全員の完了と対象一致を確認してから集計する。
重複担当/票・未完了・不正対象・別版の票があれば採用判定は未完了とし、欠けた票を賛成や反対へ補わない。
反対票・理由を消さず、3賛成でも残る注意点を採用判断へ引き継ぐ。
候補の内容や版を変更した場合は別版として扱い、古い票を流用しない。基準をその場で変更しない。

## 4. 採用と Coordinator への引渡し

採用候補は起票直前に既存Issueと作成結果を再確認し、許可された範囲で1つのIssueへ永続記録する。
実質同じ既存IssueがあればそのIssueへ対応付ける。起票権限不足や保存結果未確認は引渡し未完了とし、Discussionだけで完了にしない。
Issue へ候補ID/版・Discussion URL・投票結果・根拠・注意点・必要な本人確認を最小限引き継ぐ。
非採用や未完了も理由と再確認条件を記録し、票を取り直して採用へ誘導しない。

週次担当はIssueの保存を読み戻して確認し、Issue URLと候補/版・採否・不足を返して当該段階を終える。
Coordinatorは採用Issueを日次で確認・整理し、Issueオーケストレーターへ個別依頼する。週次担当は実装を直接起動しない。
依頼受理後の進行・検証・停止再開・重複防止はrepo側で完結させる。
起票後に必要性を再投票しない。投票はシナリオへの本人承認や外部操作・merge/deploy の権限承認を代用しない。
Issueオーケストレーターが同じIssueの既存実行、実行URL、固定base/対象head、承認、レビュー回数を照合して引き継ぐ。

## 再開記録

週範囲・repository・固定head・系統・候補ID/版、Discussion/Issue URL・コメントID、担当別の票と理由、
採用/非採用/未完了、未保存/unknown、実行URL、現在段階・停止理由・次の確認を残す。
公開可能な要約だけを保存し、外部変更の失敗と候補判定の失敗を区別する。
