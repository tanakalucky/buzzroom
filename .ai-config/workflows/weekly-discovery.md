# 週次の課題発見と採用

この手順は候補の発見・Discussion での独立投票・採用 Issue の引渡しを扱う。
外部スケジュールや自動投稿は有効化しない。[導入・接続契約](../templates/development-loop-integration.md)と
対象 repo の AGENTS.md・規約・公開範囲・各操作の許可を確認して使う。
採用後の実装は[Issue ごとの開発手順](development-orchestrator.md)へ渡し、必要性を再投票しない。

## 1. 対象と2系統を固定する

対象 repository、週の開始/終了と timezone、確認する固定 head、既存 Discussion/Issue/PR、実行URLを記録する。
repo と週範囲が同じ先行実行・記録を再取得し、再開なら既存候補と結果を引き継ぐ。
日次 Issue 対応と別の常駐サーバーや新しい実行基盤を作らない。

同じ repo/週でも、バグ発見とリファクタリング発見を別の独立した調査担当・会話の2系統で起動する。
互いの候補や判断を入力に混ぜない。
同じコードを見ても、バグは既存仕様からの逸脱・再現条件・影響、リファクタは動作を維持したまま解消する
具体的な構造上の問題・狙い・回帰リスクをそれぞれ示す。曖昧な仕様をバグと断定しない。

根拠は既存コード・仕様・失敗記録・Issue/PR・レビューの必要最小限に絞る。
対象 repo へ共有可能な安全な根拠だけを使い、秘密/ignored や生の私的ログを読まない。
private repo の情報を公開 Discussion・共通ルールへ転載しない。公開範囲が判断できなければ投稿を止める。

## 2. 候補を整理し Discussion に残す

Discussion は `repository / 週範囲 / 系統` ごとに1つとし、bug 用と refactor 用を別 Discussion にする。
候補ごとに Discussion を増やさず、各 Discussion 内の候補に `repository / 週範囲 / 系統(bug|refactor) / 候補ID / 版` と出典を付ける。
内容には問題・根拠・影響・最小案・期待する改善・未確定点を書く。バグとリファクタを同じ候補に混ぜない。
同じ原因・同じ狙いの実質同候補、既存 Issue、過去候補の重複を比較し、別名や別系統で新規起票しない。
既存 Issue があれば根拠を追記/参照し、新規候補との対応と新規作成しない理由を残す。

許可された投稿担当が対象 repo の既存 Discussion を全ページ確認し、同じキーの候補・投票記録を再利用する。
新規投稿前に現物を再取得する。再実行・再開・応答不明でも Discussion/Issue を重複作成しない。
投稿結果が unknown なら記録と現物の照合が済むまで再送しない。未保存の本文と blocker を保持する。

## 3. 独立5人の投票

候補ごとに同じ候補ID・版・根拠・評価対象を5人の新しい独立担当へ渡す。
先行票・他担当の会話・実装側の自己正当化を継承させず、1人1票で `賛成/反対` と理由を返してもらう。
担当ID・対象・完了状況・票・理由を Discussion の記録へ対応させる。投票担当は読取専用で投稿・起票しない。

独立5人中3人以上の賛成を採用基準とする。5人全員の完了と対象一致を確認してから集計する。
重複担当/票・未完了・不正対象・別版の票があれば採用判定は未完了とし、欠けた票を賛成や反対へ補わない。
反対票・理由を消さず、3賛成でも残る注意点を採用判断へ引き継ぐ。
候補の内容や版を変更した場合は別版として扱い、古い票を流用しない。基準をその場で変更しない。

## 4. 採用と Coordinator への引渡し

採用候補は起票直前に既存 Issue と作成結果を再確認し、許可された範囲で1つの Issue にする。
Issue へ候補ID/版・Discussion URL・投票結果・根拠・注意点・必要な本人確認を最小限引き継ぐ。
非採用や未完了も理由と再確認条件を記録し、票を取り直して採用へ誘導しない。

Coordinator は採用 Issue を実行ツールの既存 UI で選択・起動・追跡し、停止後は同じ実行へ継続する。
起票後に必要性を再投票しない。投票はシナリオへの本人承認や外部操作・merge/deploy の権限承認を代用しない。
同じ Issue の既存実行、実行URL、固定 base/対象 head、承認、レビュー回数を引き継ぐ。

## 再開記録

週範囲・repository・固定head・系統・候補ID/版、Discussion/Issue URL・コメントID、担当別の票と理由、
採用/非採用/未完了、未保存/unknown、実行URL、現在段階・停止理由・次の確認を残す。
公開可能な要約だけを保存し、外部変更の失敗と候補判定の失敗を区別する。
