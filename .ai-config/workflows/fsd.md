# FSDの導入・変更

[FSDルール](../rules/fsd.md)を全文読んで適用する。
新規・既存アプリとも、依頼範囲で次の順に進める。
既存アプリの一括移行、スクリプトによる設定生成、依存チェックCIの追加はこの手順に含めない。

## 1. 既存構成を確認する

対象のAGENTS・設計資料、フレームワークとルーター、ソースルート、エントリーポイント、
import設定、共有パッケージ、既存のlint・型検査・テスト・ビルド方法を確認する。
変更対象の配置と依存先・利用元を追い、既存FSDルールや例外があれば照合する。
新規アプリでは、既に選ばれた技術・配置と未作成部分を区別する。

## 2. 配置案を示す

変更対象ごとに「現在の配置（新規なら新規）→配置先・責務→公開APIと利用元」を短く示す。
必要なレイヤー・スライス・セグメントだけを選び、importの依存方向も示す。
ソースルート、エイリアス、共有パッケージ、ルーターとの対応、例外の理由は対象リポジトリの
既存設計資料やルールに記録し、共通ルールへ固定しない。
未確定のユーザー判断がある場合は[認識合わせ](clarify.md)に従って質問し、回答に依存する変更は待つ。
配置案のみの依頼は、案を示して終了する。

## 3. 必要な変更を行う

合意した範囲の配置・公開API・importと必要なローカル資料だけを変更する。
既存アプリは変更対象から段階的に適用し、無関係な移動や空ディレクトリの追加を避ける。
既存の共有パッケージ・フレームワーク規約を保ち、既存違反の全件修正へ広げない。

## 4. 確認して報告する

- 上位への依存、別スライスへの同一レイヤー参照、公開APIを迂回するimport、循環依存を変更範囲で確認する。entitiesの`@x`は記録した理由と利用先を照合する。
- 移動前のimportやルーティングが残っていないか、共有パッケージと重複していないかを確認する。
- 対象リポジトリの既存lint・型検査・関連テスト・ビルドを変更に応じて実行する。新規の検出ツールやCIを自動追加しない。
- 配置と理由、変更範囲、実行した確認と結果、未実行の確認・残存する既存違反を区別して報告する。手動でのimport確認を自動検出の保証として扱わない。
