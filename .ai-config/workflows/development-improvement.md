# 開発ループの振返りと改善

[Issue ごとの開発](development-orchestrator.md)と[週次課題発見](weekly-discovery.md)の記録から改善候補を作る。
repo側の最上位セッションが[役割と受け渡し](agent-handoff.md)を全文読み、専門分析・投票担当を直接呼ぶ。
採用改善は必ずIssueへ保存し、Coordinatorが日次でIssue担当へ依頼する。週次担当は実装を直接起動しない。
この手順は自動適用や外部スケジュールを許可しない。対象 repo の規約・共有範囲・操作権限を確認する。

## 1. 3種類の記録を別に分析する

対象 repository と分析期間、対象記録の URL/ID・版を先に固定し、次の3種類を別の独立担当に渡す。
各担当は他担当の分析・票を継承せず、原記録の事実・件数/母数・問題・根拠・改善候補・不足を報告する。

- Issue の疑問・根拠・本人の回答・決定: 確認漏れ、回答待ち、認識違いと再作業の原因。
- PR レビューと対応履歴: 指摘の発生条件、修正/除外の理由、再発と検証漏れ。P0/P1/P2 と未分類を保つ。
- 課題発見 Discussion と投票: バグ/リファクタ候補、採否と反対理由、重複や根拠不足、実際の対応結果。

分析担当は読取専用で秘密/ignored を除外し、未完了や根拠不足を問題なしにしない。
私的な会話・認証情報を記録へ取り込まず、共有可能な最小要約だけを扱う。

## 2. 横断統合と改善投票

3種類の分析の出典を照合してから横断統合する。同じ原因の候補は統合先 ID と全出典を残し、
異なる問題を件数だけでまとめない。反対・除外・未完了や観測できなかった範囲を保持する。
改善候補には問題・狙い・適用先・最小変更・副作用・検証方法・元の根拠を付ける。
まず repo 固有の改善を優先し、複数 repo へ妥当に共通化できる根拠があるものだけ ai-dev-config の候補にする。
private repo の根拠や個人情報を公開共通ルール/Discussionへ転載しない。共有できない場合は共通候補化を止める。

改善候補と独立担当別の5票・理由・採否・根拠は対象 repo の改善用 Discussion に保存する。
起票前に既存 Discussion/Issue と実質同候補を確認し、既存があれば対応付けて重複起票しない。
保存結果不明時は現物を再取得して確認し、同じ候補・版を無条件に再送しない。
改善候補も[独立5人の投票](weekly-discovery.md#3-独立5人の投票)に従う。対象版・全5票の完了を確認し、3賛成以上で採用する。
投票だけで実装や権限が承認されたとは扱わず、起票後の必要性再投票をしない。

## 3. 実施前に効果の測り方を決める

週次repo担当が採用改善をIssueへ起票/対応付けして保存を確認する。Discussionだけで引渡し完了にしない。
Issue担当への依頼前に問題と狙いに合うbefore/after指標を定義し、不足なら同Issueに保留と次回確認を残す。
一律の数値目標を発明せず、既存データと対象問題に照らし、本人の価値判断が必要なら具体的に確認する。
新機能/仕様変更のシナリオ承認は開発手順に従う。

同じ改善 Issue に次の事前定義と元データへの安全な参照を残す。

```text
改善ID・版 / 問題・狙い / 対象repo・適用範囲
before期間 / after期間 / timezone / 比較条件
指標の定義・単位 / 母数と除外条件 / 情報源URL・取得方法
成功条件 / 悪化条件 / 保留条件
実施予定・対象commit / 次の確認予定・確認担当・対象
```

期間・母数・情報源・比較条件を揃えられない、または情報が足りない場合は「保留」にし、
成功を報告せず、必要な追加データ・再確認対象・予定を引き継ぐ。
実施後に成功に合うよう基準・期間・母数を後付け変更しない。
基準変更が必要なら旧定義・理由を残して別版の将来比較にし、元の比較は保留のまま扱う。

## 4. 実施と after 確認

Coordinatorの日次依頼を受理したIssueオーケストレーターが[Issue ごとの開発手順](development-orchestrator.md)で進行し、既存の承認・レビュー・品質条件を通す。
実装進行と再開はIssue側、実施後の効果比較と同Issueへの追記は週次repo担当が担い、Coordinatorに集計を戻さない。
改善の採用と実装完了、merge/deploy、効果の確認は別状態として記録する。
対象 commit・実施日時・適用先の実結果を確認してから、事前定義に従って after データを取得する。
未実施の改善に after の成果を付けず、別 repo/別版の結果を代用しない。

同じ改善 Issue に before/after の値・母数・期間・情報源・比較条件、成功/悪化/保留と根拠を追記する。
データ不足・比較条件不一致は保留として追加データと再確認予定を残す。
悪化は原因・安全な対応案を同じ Issue へ戻し、無断の設定変更やロールバックを行わない。
再確認のために同じ改善 Issue を重複起票せず、確認予定・対象・実施状況・停止理由を引き継ぐ。

## 再開記録

分析期間/repository、3種類の出典と分析、候補ID/版、全票・理由・状態、Issue/Discussion、
事前指標の版、実施状況/commit、比較データ・判定・不足・次の確認予定を保持する。
記録と現物を再取得し、unknown の投稿/起票を無条件に再送しない。
