# 既存実行への接続・導入テンプレート

このファイルは非機密の記入用ひな形。外部設定・スケジュール・投稿・merge/deploy を有効化しない。
導入担当が対象 repo と本人の許可を照合して使い、非公開 automation prompt・個人情報・秘密をこの repo へ転記しない。

## 接続契約

| 項目 | 記入する内容 |
| --- | --- |
| 対象 | repository、本人/依頼元の公開可能な出典、許可範囲と禁止操作 |
| 本人と出典の識別 | 接続先の本人識別根拠、本人発言/既存許可内の採用候補/代理投稿/引用/第三者の区別、代理投稿ID台帳への安全な参照 |
| 既存実行 | 既存の日次タスク識別子と管理先への安全な参照、実行URL取得方法、担当者 |
| Coordinator | 担当（AIまたは人間）、実行ツールの既存 UI（例: Dots UI）の対象環境、起動/継続操作、結果の取得場所、停止と再開の責任者 |
| 入力 | Issue URL、固定base/対象head、branch/PR、段階、停止理由、承認対象と回答、レビュー回数、既存記録 |
| 出力 | 状態・次の動作・不足、branch/commit/PR、checks、保存確認、次の確認対象 |
| 冪等性 | repo/Issue と既存実行、週範囲/repo/系統/候補ID/版と既存Discussion/Issueの照合方法 |
| 品質証拠 | CI/run、独立3観点、preview deployment URL/SHA、シナリオ→E2E/runの対応 |
| 投稿境界 | 公開範囲、投稿可能な担当と対象、秘密除外、unknown時の現物再取得方法 |
| 停止 | 新規起動を止める既存の操作、進行中の状態確認、保存先、再開条件 |

本人が確認した特定環境の Codex ブラウザによる起動/継続 UI と既存 Pro 利用枠の情報は、その環境の接続根拠として扱う。
全環境の能力や追加費用ゼロを保証しない。CLI/API を必須にせず、未使用の経路を検証済みとしない。
新規契約・課金・認証情報作成、別の常駐サーバー、日次処理を置換する新基盤を導入しない。

## 既存日次の更新用ひな形

導入時に既存タスクの非機密な作業指示へ適用する。識別子・secret・私的本文は記入しない。

```text
対象repoの採用済みIssueと既存実行を確認する。
出典URL/IDだけで本人承認にせず、接続先の本人識別と既存許可を照合する。
本人アカウントの代理投稿IDを引き継ぎ、質問/記録・引用・第三者コメントを新たな本人承認にしない。
出典が区別できなければ、依存する外部変更と承認判断を止めて確認する。
既存実行があればCoordinatorが実行ツールの既存UIで同じ実行を継続し、新規重複起動しない。
未実行の採用IssueだけCoordinatorが同じUIで起動し、実行URLと出典を引き継ぐ。
development-orchestrator入口から対象repoの共通本文を全文読む。
通常PRを既定とし、現行の本人個別指示だけを例外として扱う。
停止後は承認対象/回答/固定base/対象head/レビュー回数/既存記録を引き継ぐ。
結果不明の起動/投稿/dispatchは現物を再取得し、無条件に再送しない。
週次候補発見はweekly-discovery、振返りと効果測定はdevelopment-improvementを使う。
操作許可の範囲を超えず、未実行/未完了/保留を成功にしない。
```

## 安全な導入・移行

1. 既存の日次タスク・作業ツリー・PR・実行中の Issue と設定を読み、対象を特定する。既存動作を保存し、新規タスクを重ねない。
2. 対象 repo の配布物を差分統合し、コピー後のリンク/入口/標準テストと helper の合成 fixture を確認する。
   これらは外部 UI や実モデルの動作確認を代用しない。
3. 既存の日次指示に Draft 既定が残っていないか確認し、通常PR既定へ統一する。現在も有効な本人個別の Draft 指示は維持する。
   既存 Draft PR は対象/所有者/現在の明示指示を照合し、通常への移行が許可されたものだけ変更する。
   PR を作り直したり、レビュー記録や回数をリセットしたりしない。
4. 本人の導入許可を得た担当だけが既存タスクの設定を更新する。このテンプレートを保存しただけでは更新済みとしない。
5. 外部副作用のない合成確認後、別途許可された対象だけ実 UI の起動/継続・出典・状態保存を確認する。
   週次スケジュール・外部自動投稿・自動merge/deployはそれぞれ現在の明示許可なしに有効化しない。

## 停止と再開

停止時は新規起動を抑止する既存の許可済み操作を導入担当に依頼し、実行中の対象と現状を再取得する。
停止が確認できなければ停止済みと報告しない。進行中の実行を無断で削除/破棄せず、実行URL・branch/PR・
固定base/対象head・段階・停止理由・回答待ち・承認対象・レビュー回数・既存記録を保持する。
再開前に本人の許可、現物との一致、同じ Issue の他実行がないことを確認し、同じ記録から継続する。
設定を戻す場合も外部変更の許可を別途確認する。権限や認証を緩めて復旧しない。

## ローカルの合成確認

[実行補助](../helpers/orchestrator_dry_run.py)は提供された証拠の整合性だけを確認する Python 標準ライブラリの dry-run。
実 API への接続、外部操作、権限の強制、実モデルの動作や証拠の真実性の保証は行わない。
入力例と否定ケースは[合成 fixture](../tests/fixtures/orchestrator_dry_run.json)を参照する。

```sh
python3 .ai-config/helpers/orchestrator_dry_run.py --fixtures .ai-config/tests/fixtures/orchestrator_dry_run.json
```

`startup`（重複・unknown・承認・再開）、`quality`（同headの品質証拠）、`vote`（独立5人3賛成）、
`weekly`（候補と既存記録）、`effect`（事前基準と比較不足）を分ける。厳密な入力は helper と fixture の契約に従う。
`startup`/`quality` は変更種別を受け取り、新機能・仕様変更には対象版への本人承認、既存バグ・動作維持リファクタには
既存仕様/動作維持の根拠を要求する。後者にも検証シナリオ ID/版と E2E の対応を残す。
週次の Discussion は repo・週範囲・timezone・系統で照合し、その中の候補 ID/版と起票先は別に引き継ぐ。
