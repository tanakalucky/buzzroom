# PRへのレビュー記録

指揮者が実装者子の実装と必要な検証の結果を照合したら、レビューを始める前に通常PRを作成する。
ユーザーがDraftを指定した場合はそれに従い、対象ブランチのPRが既にあれば再利用する。
[記載方針](../rules/documentation.md)に従ってテンプレートの原文を読み、PR本文は変更概要と関連Issueを中心に簡潔にする。
PRコメントは下記の記録テンプレートに限定し、管理用の証拠・照合・履歴は指揮者が内部記録に保持する。READMEへ作業履歴を追記しない。

## 担当と権限

- PR作成・push・コメント投稿は指揮者がタスクで許可された範囲で行う。この手順自体は外部変更の許可にならない。
- 実装者子は結果を指揮者へ返すだけでPR操作・投稿を行わない。レビュー入口と観点担当は[共通方針](policy.md)の読取専用を守り、記録用の結果を返すだけで投稿・修正しない。
- レビューだけの依頼ではPRを新規作成しない。PRや投稿権限がない場合は同じ形式で指揮者へ返し、PR記録は未完了と明記する。投稿できないことを指摘なしにしない。
- [ラウンドの共通定義](rounds.md)の最大3回・独立3観点・P0/P1収束条件を維持する。投稿や再開のために回数をリセットせず、記録の再送だけでレビューを再実行しない。

## 記録の単位と再開

1. 指揮者は対象PRの既存コメントを全ページ確認し、内部記録と照合し、下記のPR/task/roundの対応、固定base、対象状態、指摘IDと対応履歴を引き継ぐ。継続タスクの記録が不明ならラウンド1へ戻さず未完了とする。
2. 1ラウンドにつき1コメントとし、最初の呼出前に対象状態と3観点の`pending`を内部記録に残す。完了・失敗・修正後は同じコメントを更新する。初回を含め、同じコメントの更新でも原判断・元の重要度・理由を内部記録から消さず、変更を追記する。
3. 投稿・更新前に同じPR/task/roundの既存記録とコメントIDを再確認する。新規投稿は対応する記録がない場合だけ行い、既存なら記録したIDを更新する。重複や他の実行との競合があれば投稿を止めて確認する。
4. 応答が不明な投稿はPRから再取得して成否を確認し、確認できるまで再送しない。失敗や投稿権限不足なら未保存の本文と対象PR・コメントIDを指揮者が保持して報告する。保存失敗を保存済みやレビュー失敗と混同しない。

マーカーは `<!-- ai-dev-config-review:v1 task=<task-id> round=N -->`（Nは1〜3）。記録はPR/task/roundで識別し、同じPR内の別の承認済みタスクを区別する。
同じタスクの継続ではtask ID・固定base・累積回数を引き継ぎ、別task IDを付けて上限をリセットしない。
旧形式 `<!-- ai-dev-config-review:v1 round=N -->` は消さず、依頼・固定base・履歴から元のタスクへ対応付けて継承する。対応が不明なら新規扱いにせず未完了として確認する。
指摘IDはPR内で `F001` から未使用の連番を指揮者が割り当て、同じ問題の再指摘・修正・再確認では同じIDを使う。
複数観点の同じ指摘は1つのIDへまとめ、全ての出典を残す。後で重複と分かった別IDは消さず、`duplicate`と統合先IDを残す。
統合で除外する候補にもIDを付ける。根拠不足を誤検出と断定せず、判断理由に不足する根拠を書く。

## 内部記録と照合の完了条件

固定baseと由来、担当ID・ツール・状態、確認範囲・実行証拠、候補件数・全出典・指摘ID・対応履歴・保存IDは内部記録に保持し、毎回のコメントには表示しない。
各担当から採用・除外・未分類を含む全候補を集め、担当別の候補件数と出典を確定してから記録を作る。
内部記録で全候補の出典→固定ID→対応履歴を全件照合し、公開する指摘は該当コメントにも対応付ける。重複を同じIDへ統合した場合も全ての出典との対応を残す。
漏れ・件数不一致・出典不明があれば記録は未完了とし、不足を報告する。保存後の本文を公開予定の内容と照合し、照合結果と保存確認を内部記録に残す。
記録の補完だけでレビューを再実行したり、ラウンド番号を進めたりしない。

## 記録テンプレート

指揮者が1回1コメントにまとめる。各回の対象・結果は必ず残し、指摘の詳細は新規指摘と判断変更だけを書く。
前回から変わらない指摘や全変更ファイル一覧は再掲せず、既存コメントのID/リンクを内部記録で参照する。
前回の未解決IDは内部記録で追跡し、収束判定に含める。新規指摘なしを未解決なしと扱わない。
これは記録の簡略化であり、毎回のレビュー対象は同じ固定baseからの累積全task差分のままとする。

```markdown
<!-- ai-dev-config-review:v1 task=<task-id> round=<N> -->
## レビュー記録（第<N>回）
- 対象コミット: <完全HEAD SHA。未commit差分があれば対象を識別できるよう明記>
- 結果: <指摘なし/P0・P1収束/再レビュー待ち/上限到達・未収束/未完了・収束未確認などの判定。未完了や停止の場合は理由>

### <指摘の短いタイトル>
- 重要度: <P0/P1/P2/unclassified>
- 内容: <該当箇所、事実と影響>
- 対応: <修正内容/見送り理由/未対応。必要な検証結果または未実行>
```

`<...>`は確認済みの値に置き換える。新規指摘・判断変更がなければ指摘欄を省略する。
全3観点が完了し未解決がない場合だけ、結果を「指摘なし」とする。
公開する項目はレビュー回・対象コミット・結果と、指摘ごとのタイトル・重要度・内容・対応だけとする。
「確認」「備考」などの欄は追加せず、管理情報を他の欄に詰め替えない。

## 内部記録で保持する情報

初回の全候補（除外・未分類を含む）と、後続回で新しく出た候補には必ずIDを付ける。
継続候補は同じIDへ新しい出典を追記し、判断変更は以前の判断を残して変更理由とともに記録する。
確認範囲・全変更パス・検証の詳細は安全な既存記録への参照でよいが、当該対象の証拠を辿れない場合は未確認とする。
未完了・失敗時は件数を0にせず未確定とする。
保存確認はコメントID・URLとともに内部記録に残す。

観点の状態は `pending` / `completed` / `failed` / `incomplete`。担当の完了通知と検証の実行は別に扱い、
実行者・操作・対象・観測結果を対応させる。子のログが見えなければ「子担当の申告、親ではログ未確認」、
テストを実行していなければ「未実行・読取判断」と書く。モデル・権限等の未確認条件を保証済みとしない。

指摘の重要度は `P0` / `P1` / `P2`。初出対象・元の重要度・出典は保持し、再評価による変更は対応履歴に理由付きで追記する。
元重要度がない候補は重要度欄を`unclassified`（未分類）とし、重要度未付与とその理由を記録する。自動的にP2へ分類しない。
分類または根拠付きの除外は対応履歴に追記し、元の未分類という事実と出典を保持する。
未解決の`unclassified`候補は未解決IDに含め、P0/P1が0件・収束とは扱わない。重要度の判断が済むまで判定は「未完了・収束未確認」とする。
対応対象は判断や修正を行った状態を示し、修正した場合は修正commitも記す。PRの最新headだけで初出対象を上書きしない。
未commit差分は明示パスと差分の識別情報を指揮者が保持し、再現できない状態は未確認とする。

結果は `open`（未解決）/ `fixed`（修正済み）/ `no_action`（対応不要）/ `false_positive`（誤検出）/ `duplicate`（重複）。
理由は全結果に必須。`no_action`は対応不要の根拠、`false_positive`は指摘が成立しない根拠、`duplicate`は統合先IDを書く。
判断変更時は内部記録の以前の記述を消さず、コメントとの対応も保持して履歴を残す。`fixed`でも修正後の検証と再レビューが未実施ならそのまま明記する。
未解決のP0/P1を`no_action`で収束扱いにせず、修正後未レビューの状態も収束としない。最終的な収束は共通定義だけで判定する。

公開する記録は事実と必要最小限の根拠に絞る。秘密情報・認証情報・生の私的ログは転記せず、安全な要約に置き換える。
この手順は記録の保存までを扱い、自動集計や開発ルールの自動更新は行わない。
