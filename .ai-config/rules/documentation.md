# ドキュメントの記載方針

## 共通の原則

- 目的・使い方・必要な制約を簡潔に書き、重複や過剰な説明を避ける。
- 同じ説明は正本にまとめて参照し、作業経過や個別の検証結果はPR本文や作業報告に分ける。
- 短縮によって意味を変えず、理解や安全な実行に必要な条件・制約・安全境界を残す。

## PR作成

PR作成前に、対象リポジトリのPRテンプレートを原文で全文読む。なければ所有者の`.github`リポジトリの共通PRテンプレートを探して同様に読む。HTMLコメント内の案内にも従う。
`gh pr create --body`・`--body-file`やAPIで本文を直接渡す場合も、この読み込みを省略しない。

## README

- READMEは利用者向けの説明に絞り、目的・使い方・設定方法・仕様・対応範囲・既知の制約を書く。
- 未実施・未検証・確認待ちなどの一時的な作業状況、個別のテスト結果、レビュー回数・指摘件数、対応履歴は書かず、PR本文や作業報告に残す。
- 製品の仕様・対応範囲・既知の制約は、利用者が知る必要のある内容を書く。詳しい経緯はIssueやPRへ分ける。

「実デプロイ未検証」は一時的な検証状況なのでREADMEには書かず、PR本文や作業報告に残す。
「SSR 未対応」「初期状態ではデプロイ無効」は製品の対応範囲や仕様なのでREADMEに記載してよい。

テストの実行方法は使い方として記載してよいが、「テスト58件成功」「レビュー3回終了」
といった個別作業の結果は記載しない。
